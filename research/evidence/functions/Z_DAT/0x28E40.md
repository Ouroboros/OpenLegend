## 2. 入口链

机器入口按下列顺序执行：

1. 保存scene id，设置场景状态并打开对应场景档案；
2. 初始化坐标、视口、方向、动画/天气状态；按metadata入口音乐与当前音乐比较后按需切换；
3. 加载目标 `SMP/SDX`，调用 `sub_29B3C` 推进一次事件图片；
4. `sub_29D2D`重绘目标场景，`sub_3D6D1`立即present；
5. 调用 `sub_3CD17`执行65帧fade-from-black；
6. 调用 `sub_2C0BB`显示场景标题，再检查脚下 `sub_2B3B4` 自动事件。

唯一调用者在每条获准进入路径上都先present世界帧并执行64帧fade-to-black，因此步骤4的目标场景present使用黑palette。步骤4的一次黑帧与步骤5的首个黑帧是两个独立present，入口淡入侧总数严格为 `1 + 65 = 66`。

## 3. 稳定循环

每次循环先保存当前BIOS tick，再调用 `sub_29B3C` 推进事件图片。输入最多消费一个动作，固定优先级为：

`left -> up -> down -> right -> interact -> main_ui -> weather_disable -> idle_update`

动作或idle分支汇合后无条件执行 `sub_29D2D` 重绘与 `sub_3D6D1` present。之后才递增五tick计数；余数为1时执行palette周期更新。随后依次执行：

1. 脚下自动事件；
2. 三个出口格检查；
3. 内部场景跳转检查；
4. 忙等BIOS tick不再等于本轮保存值，再进入下一轮。

独立oracle固定首20 tick的周期点为 `[1, 6, 11, 16]`，84条metadata共有252个出口格槽和10处非负内部跳转。SDL平台在输入前读取 `frame_tick`，调用 `LegacyGameRuntime::advance(frame_tick)`，帧末通过 `wait_for_tick_change(tick_source, frame_tick)`兑现同一tick边界；参数为空的测试调用只是确定性协作驱动，不改变生产平台节拍。

## 4. 内部跳转与退出

内部跳转在自动事件与出口格之后判定。命中时先调用64帧fade-to-black并归档旧场景，再切换scene id；若源场景主入口1的X/Y均为0，则使用目标metadata jump-return坐标，否则使用目标普通入口坐标。随后重新初始化目标场景、按需切换音乐、加载 `SMP/SDX`、推进事件图片、重绘并present黑色目标场景，再执行65帧fade-from-black、标题与自动事件。目标场景淡入侧同样严格为66次present。

退出路径清除九个场景键状态，执行64帧fade-to-black，恢复世界资源和场景退出音乐后返回。唯一调用者按保存的进入方向映射 `[3, 2, 1, 0]` 反转世界方向，清步行offset并恢复反向基础玩家图；随后黑色世界帧与65帧世界淡入仍由该caller职责处理。

## 5. 汇编 → C++ 单向对照与修正

`SceneSession::tick/finish_tick_after_action/finish_tick_after_scene_present/finish_tick_after_auto_event/resolve_scene_transition/complete_scene_jump`以显式continuation恢复同步主循环边界；`LegacyGameRuntime`只消费一个按机器优先级聚合的动作，并在每个present完成后续行。入口、动作present、五tick周期、自动事件、出口优先于内部跳转、场景档案/音乐和caller方向恢复均与机器一致。

本轮发现一项新增差异：现代runtime原先把机器“目标场景黑色present”和 `sub_3CD17` 的首个黑帧合并为同一帧，入口及内部跳转均只有65次present。修正后仅场景入口和内部跳转的 `fade_from_black`结果携带 `repeat_initial_fade_frame`；runtime在65帧palette序列前复制首帧，恢复两个连续黑帧及总计66次present。opcode 13等没有机器前置present的普通fade不受影响。

真实runtime测试逐帧断言入口前两帧均为同一目标场景像素和全黑palette，并在第66次present后继续标题/初始事件；内部跳转结果单独断言同一标记。Linux app Debug根构建14/14通过。

## 6. Oracle、closure与结论

独立生成器直接读取原始 `Z.DAT`、`RANGER.GRP` 和 `KDEF` 资产，固化函数/调用者机器身份、入口与内部跳转的 `1+65` 帧序列、循环顺序、输入优先级、tick边界、周期点、出口与跳转metadata以及caller方向映射。B7场景owner关闭时，正式覆盖前已独立生成两次并逐字节比较一致。

B7本项只关闭 `scene-event-closure.tsv` 中 `target_owner=scene` 的主循环职责，当时同址 `input-font-closure.tsv` 的输入owner保持未关闭。`sub_29391`、`sub_295D0`、`sub_296E6`、`sub_29819`、`sub_299A1`、`sub_29B3C`、`sub_29C36`、`sub_29D2D`、`sub_2B3B4` 等delegated helper的closure不由本项传播。

## 7. input-font owner最终REVIEW与修正

input-font `audit_order=18`以新的只读IDAT副本从同一入口独立冻结：唯一外部入口和直接caller为`sub_25911:0x25A2A`，函数内部无外部入口，唯一`RETN @ 0x29390`。40个callsite/target、116项重定位和`0x28F1A..0x290A0`输入分派切片均进入机器门；输入切片SHA256为`fddf83fdce107f990f26149bb68f68f624bcd1a02c785e494056c33d4caa0e8b`，退出九键清理`0x292E0..0x2931F`切片SHA256为`70df462ae55a69fcb8672ab92b025cb2bf95055f4cfdec5d09340c990ef6b785`。

独立机器合同确认每tick至多一个动作，优先级严格为`left -> up -> down -> right -> interact -> main_ui -> weather_disable -> idle_update`。方向和确认组按完整非零byte判断；Escape和L只测试bit 0。方向命中时先清两个别名再调用movement；interaction先同步调用`sub_29C36`再清Enter/Space/Insert三键；UI先同步调用`sub_212C0`再清Escape bit 0；weather先写场景天气/阴影状态0再清L bit 0。任何高优先动作均不清低优先键态。

首轮C++对照发现现代SDL/runtime把interaction/UI/weather从单个keydown锁存为布尔请求并立即回收键态：低优先键即使在后续tick前已keyup仍会延迟触发，且三类回收顺序早于机器的delegated call。该轮结论立即作废。最小修正后，SDL把当前`LegacyKeyboard` byte state在帧边界交给runtime；runtime只选择当tick最高优先动作，不锁存低优先输入；`SceneSession`把所选动作的reset token保持到对应同步continuation返回，并在公共scene-tail present前发出。方向别名仍在movement前清除。
