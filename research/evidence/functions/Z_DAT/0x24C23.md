# 函数证据：`sub_24C23` `0x24C23..0x24C8D`

状态：`platform_adapted`

来源：当前 `Z.DAT` 机器码；审计包 `tmp/startup-review/0x24C23.txt`

## 1. 独立机器恢复

- 入口先建立8字节栈帧。
- 随后无条件依次打开 `EARTH.002`、`BUILDING.002`、`SURFACE.002`、`BUILDX.002`、`BUILDY.002`。
- 每次打开返回的16位句柄分别写入独立全局；函数返回最后一个 `BUILDY.002` 句柄。
- caller为`main`，调用位于`sub_247DD`共享资源初始化之后、标题流程之前；五个句柄保持到统一shutdown。

## 2. 汇编 → C++ 映射

- 五层固定顺序：`world::WorldMapData::kLayerLoadOrder`与`WorldMapData::WorldMapData`。
- 标题前建立及会话期owner：`app::LegacyGameRuntime::world_map_`；成员在标题renderer之前构造，进入新游戏或编号读档时只建立`WorldSession`，不重读五层文件。
- 原句柄读取：`resource::DataRoot::read`；每层按460,800字节的16位little-endian cell解码。
- shutdown由`LegacyGameRuntime`成员逆序RAII承担，所有world/scene/session使用者销毁后才释放驻留层。

## 3. 差异与整轮重启

1. 早期实现曾把`SURFACE`放在错误位置，已按机器顺序修正。
2. 本轮从入口恢复后发现`WorldMapData`仍延迟到首次`start_world`建立，标题前缺失层不会失败，且新游戏/读档会重复读取；该轮立即废弃。
3. 将`world_map_`前移为runtime启动成员，移除新游戏、载入及session失败路径对地图owner的重置，`start_world`仅复用缓存。
4. 再次从`0x24C23`入口逐指令覆盖五次open、存放顺序、caller时点及会话期生命周期；合法资产域零新增差异。

## 4. 平台适配

- 原DOS句柄常驻改为文件整包读取后立即关闭、解析字节常驻；只读合法资产产生相同cell值。
- 原函数不检查open失败；现代在标题前报告首个失败文件并阻止进入标题，避免无效句柄后续读取。
- 容器和checked little-endian解码阻止截断输入造成宿主越界。

## 5. 验证与结论

- Linux app Debug `proc_96cf`：14/14。
- 回归确认缺失`EARTH.002`时标题前失败；runtime构造完成后删除全部五层源文件，编号槽仍可载入并进入world，证明后续复用启动owner而非延迟重读。
- 原程序动态差分：`blocked_runtime_oracle`。
