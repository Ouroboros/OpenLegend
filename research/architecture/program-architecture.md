# 《金庸群侠传》DOS 版原程序架构基线

版本：v1  
状态：架构调研收敛稿  
范围：`Z.COM`、`Z.DAT`、原版数据文件及现有 IDA 9.2 headless 导出

## 1. 目标与停止线

本文只回答后续重写必须先知道的问题：

- 原程序由哪些大模块组成；
- 各模块拥有哪类状态；
- 启动、普通帧、场景、战斗、菜单、存读档和退出如何协作；
- 哪些行为属于 DOS/VGA/Miles 等平台边界；
- 哪些未决问题只影响模块内部，不应继续阻塞工程架构。

本文不要求在实现前恢复全部函数、全部事件指令、全部战斗公式或每个结构字段。继续下钻如果不会改变模块边界、主要依赖方向或首个公共接口，就应留到对应模块工作包。

## 2. 证据等级

- **高可信推断**：有调用链、数据布局和多个消费者共同支持，但尚未动态执行验证。
- **模块内未决**：需要在实现该模块时继续确认，不影响本文架构。

## 3. 启动链与进程生命周期

```text
PLAY.BAT
  -> Z.COM
       -> DOS EXEC LOGO.SCR
       -> 恢复文本模式
       -> 显示发布/破解提示
       -> 等待按键或约 3 秒
       -> DOS EXEC Z.DAT
            -> Watcom 32-bit DOS/4GW LE 主程序
            -> 初始化字体、输入、音频、资源和游戏状态
            -> 标题/新游戏/读档
            -> 世界主循环及同步模态流程
            -> 恢复硬件/中断/音频并退出
```

结论：

- **已确认**：`Z.COM` 是启动器，不是游戏逻辑主体；核心逻辑位于 `Z.DAT`。
- **已确认**：`Z.DAT` 的 `main` 位于 `0x20D35`。
- **高可信推断**：现代重写不需要保留 DOS `EXEC` 边界，可把启动器表现合并为 `app` 的启动状态；是否复现破解提示属于产品决定，不影响游戏核心。

## 5. 关键数据组织

### 5.1 通用资源

- 普通 `.IDX` 是小端 `uint32` 累计结束偏移。
- 图像帧为 8 字节头：`width`、`height`、`xOffset`、`yOffset`，均为小端 16 位。
- 帧正文逐行编码：行长度字节，随后重复 `skip`、`run`、`run` 个像素。
- 底层绘制函数直接执行上下左右裁剪，并把 `(x - xOffset, y - yOffset)` 作为左上角。
- 原调用层把精灵原始编号除以 2 后索引帧，因此地图/动作数据中的精灵编号存在“偶数编码”合同。
- `SDX/WDX` 的前 `N-1` 项为累计结束偏移，最后一个零为哨兵，末项延伸到 EOF。

### 5.2 世界与场景

- 世界地图五层均为 `480 × 480 × int16`。
- 世界运行时使用约 `128 × 128` 缓存和 `32 × 32` 菱形视口，投影格距约 `18 × 9`。
- 单场景地图记录为 `6 × 64 × 64 × int16 = 49,152` 字节。
- 单场景事件记录区为 4,400 字节。

### 5.3 会话与存档

`RANGER.GRP` 六段：

1. 836 字节头；
2. `320 × 182` 角色记录；
3. `200 × 190` 物品记录；
4. `84 × 52` 场景元数据；
5. `93 × 136` 武功记录；
6. `5 × 30` 商店记录。

文件角色：

- `ALLSIN` / `ALLDEF`：只读基线；
- `ALLSINBK` / `ALLDEFBK`：当前游戏工作副本；
- `S1..S3`、`D1..D3`、`R1..R3`：三槽存档的三组组成文件。

架构含义：原程序把大量业务状态保存在几块共享二进制区域中。现代实现不能把这种共享裸内存直接复制为跨模块全局变量，应为每块可变状态指定唯一所有者和显式导入/导出合同。

### 5.4 文本与字体

- `TALK.GRP` 共 2,977 条记录；正文逐字节 `XOR 0xFF` 后为 Big5，2,976 条可直接解码。
- ASCII 字体为 8×16，每字形 16 字节。
- Big5 字体为 16×16，每字形 32 字节。
- Big5 字形索引按 lead/trail 计算，并通过 64 项环形缓存从 `FONT3.C16` 按需读取。
- 原始字形位图按 MSB-first 写入 8-bit framebuffer；设置位同时写前景/阴影两个相邻像素值。

## 6. 渲染与帧时序

### 6.1 framebuffer

- **已确认**：逻辑画面固定为 `320 × 200 × 8-bit indexed`，共 64,000 字节。
- **已确认**：所有绘制先进入 RAM framebuffer；呈现时整块复制到 VGA `A000:0000`。
- **已确认**：清屏、矩形、RLE 精灵和字体都直接写该 framebuffer。
- **已确认**：调色板为 256×RGB，每通道原值为 VGA 6-bit；写 DAC 前等待垂直回扫状态。

### 6.2 时间

- `dword_544D8` 的初始值是 `0x046C`，即 BIOS tick 计数器地址。
- 原程序等待逻辑按 tick 变化忙等；典型频率约 18.2Hz。
- 现代实现应保留“逻辑 tick 和调用顺序”，但平台后端不得复制忙等，可使用单调时钟和让出/睡眠实现等价等待。

## 7. 运行时交互

### 7.1 初始化

```text
app
  -> resource：定位并打开原版数据
  -> render：建立 320×200 framebuffer、字体和调色板状态
  -> input：安装/初始化键盘状态
  -> audio：初始化 Miles/XMI/WAV 播放状态
  -> game data：装入基线或工作副本
  -> UI：进入标题/新游戏/读档流程
```

### 7.2 普通世界帧

```text
采样输入与 tick
  -> 世界移动/碰撞/入口判断
  -> 触发请求：场景、对话、菜单或战斗
  -> 更新周期状态
  -> 绘制世界与 UI
  -> 提交 framebuffer
  -> 音频维护
```

原程序存在大量同步、阻塞式模态调用。现代重写可以改成显式状态机，但同一逻辑 tick 内的请求消费顺序不能随意改成异步消息总线。

### 7.3 场景/剧情

```text
app 收到 EnterScene
  -> scene 装入 6 层地图与事件区
  -> scene 处理移动和事件触发
  -> talk 解码/显示文本
  -> scene 返回：继续、回世界、开菜单、开始战斗或退出
```

场景事件的完整指令集合属于模块内未决；其存在不会改变 `scene -> typed result -> app` 的边界。

### 7.4 战斗

```text
app 收到 StartBattle
  -> battle 装入 FIGHT 资源和参战者快照
  -> battle 自己维护输入、动作、AI、绘制和胜负状态
  -> 返回 Victory / Defeat / Escape / Continue
  -> app 按原顺序提交战后状态并恢复来源模式
```

### 7.5 保存与读取

```text
保存：各状态所有者 -> 会话快照 -> persistence -> S/D/R 槽文件
读取：persistence -> 校验并解析槽 -> 按固定顺序导入各所有者 -> app 切换模式
```

持久化只运输和重建状态，不应成为世界、场景或战斗规则的所有者。

## 8. 平台边界

必须从业务核心剥离：

- DOS `EXEC`、文本模式和中断向量；
- VGA Mode 13h、`A000:0000`、DAC 端口和垂直回扫；
- BIOS tick `0x046C` 和忙等；
- IRQ1 键盘扫描码；
- Miles XMI/WAV 播放 API；
- DOS 文件路径与文件句柄。

必须在核心保留：

- 320×200 indexed framebuffer 和原始调色板值；
- RLE、裁剪、字形和地图投影规则；
- 输入边沿/持续状态在游戏逻辑中的消费顺序；
- tick 驱动的动画与等待语义；
- 原始资源 ID、记录布局和状态迁移；
- 场景、菜单、战斗和存档的同步切换顺序。
