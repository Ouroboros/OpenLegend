3.1 NG+ All-in-One TOML存档

启用NG+后，从一周目开始，普通存档和通关存档都以一个UTF-8 TOML文件保存恢复游戏所需的状态。

加载时先从指纹匹配的当前GAME DATA建立静态定义，再按数据性质恢复：权威运行状态完整保存，静态定义只引用GAME DATA，S／D世界状态分别保存为完整bytes，经Zstandard压缩后编码为Base64。

All-in-One表示这些状态与NG+扩展都在同一个TOML中，不使用sidecar。

3.1.1 格式分流与用途

[new_game_plus]
enabled = false  # 是否启用NG+存档格式与加载优先级
条件与用途 保存格式 路径
enabled=false的普通存档 现有Legacy D／R／S，字节布局不扩充 存档根目录中的R1.GRP／S1.GRP／D1.GRP … R999.GRP／S999.GRP／D999.GRP；继续共享原版RANGER.IDX
enabled=true的全部周目普通存档 GAME DATA静态基线＋分类持久化状态的All-in-One TOML；一周目起即使用 ngplus/001.toml … ngplus/999.toml
enabled=true的一周目起通关存档 相同结构、只用于创建下一周目的All-in-One TOML completed/001.toml … completed/999.toml
  • 普通读档固定使用以下优先级；>表示同一槽位中左侧格式优先： 
    若 enabled=true：TOML > Legacy D／R／S
若 enabled=false：只读取 Legacy D／R／S
  • enabled=true时，同槽位存在普通TOML就只验证并加载TOML；只有不存在TOML时才读取Legacy D／R／S。TOML存在但损坏或不兼容时必须报告错误，不得静默回退到可能较旧的Legacy状态。
  • enabled=false时，普通读档扫描、列表和加载都只处理Legacy D／R／S，完全忽略普通TOML和通关TOML；磁盘上的TOML保持不变。
  • Legacy读档路径始终保留：关闭NG+时它是唯一读档格式；开启NG+时它是同槽位不存在TOML时的后备格式。关闭NG+时普通保存继续写Legacy；开启NG+时无论当前是第几周目，普通保存都写All-in-One TOML。

  • 保存格式不决定运行时属性宽度：角色数值属性及伤害、医疗、内伤、中毒、解毒等战斗结算数值在内存中统一为signed 64位。

    向Legacy D／R／S写出时，须在任何16位编码之前逐字段检查原版对应的有符号／无符号16位可表示范围及字段合法域；关闭NG+的Legacy模式仍允许原版普通物品把抗毒合法加到100以上。任一值不能无损表示即拒绝整次保存，保留原存档，不截断、夹值或回绕。

    写入新TOML时，这些逻辑整数直接使用signed 64位，不因Legacy格式另加16位限制；内伤按存档周目与当前CFG算出的HurtMax(n, CFG)校验，中毒量按固定0～99校验，其他永久能力（包括抗毒）不按周目上限拒绝或夹值。固定枚举与字段不变量仍须校验；非法状态拒绝保存或读回。

    只对实际写入存档的字段做编码检查，战斗临时伤害量不会因此变成Legacy存档字段。详细边界见第3.1.4节。

  • 开启NG+后加载Legacy存档时，先按Legacy格式完整解码，再无损扩宽合法抗毒等数值并纳入NG+权威状态，不按目标周目上限夹值，也不回写原Legacy文件。其后执行普通保存时写入新的TOML，此后同槽位读档由TOML优先。

  • Legacy没有NG+专属历史字段。转换时，每名角色的ever_joined统一初始化为false（逻辑值0）， 全部no_magic_count[ItemCount]统一初始化为0；

    不得根据当前队伍、剧情状态、人物属性或物品状态反推旧历史。转换后的正常入队与无关联秘笈成功事件再从这些初始值开始记录。

  • 两类TOML都不使用sidecar，不混合读取同槽位D／R／S，也不能导出为Legacy格式。不得用一种统一的“全存”或“全差量”策略处理全部数据；各类状态必须严格使用第3.1.3节规定的完整状态、静态引用或完整压缩bytes表示。
  • 普通TOML可从存读档界面直接恢复游戏；通关TOML只能由标题菜单的“New Game+”入口读取，不能作为普通存档加载。
  • 一周目通关TOML也使用本节定义的完整结构；从通关TOML创建下一周目时，才执行第1章规定的人物、物品、故事状态和新周目初始状态转换。
  • 同一编号的Legacy与普通TOML可以同时存在于磁盘，但普通读档界面把它们视为同一个逻辑槽位并按上述优先级选择来源。通关TOML位于独立目录，只出现在启用NG+后的“New Game+”来源页面。

  • 当前已加入NG+ TOML内存编解码与单文件读写，游戏入口尚未接入；本节是format_version=2的唯一正式定义。首个完整存读档实现完成后，任何不向后兼容的结构变化必须提升格式版本；只改变规则语义时必须提升规则版本。
  • format_version描述TOML结构；ruleset_version描述生成和解释存档所用的NG+规则。
  • 当前正式格式不包含任何已经删除的旧版生命／内力参考字段。历史评审文档中的此类字段不构成兼容输入；TOML出现相应未知键时按严格验证规则拒绝。

3.1.3 原版审计与分类型持久化

原版为了直接保存运行时内存，把RANGER六段与完整S／D写入存档。R#.GRP固定为114,242 bytes， RANGER.IDX六个累计尾为[836,59076,97076,101444,114092,114242]；

S#.GRP为4,915,200 bytes，D#.GRP为440,000 bytes。

当前Legacy加载也会把这六段固定记录和S／D字节整体复制进临时快照，通过长度与结构验证后整份提交，不会逐字段与当前GAME DATA合并。

现代TOML按数据性质选择表示，不采用统一差量策略：属于权威运行状态的数据完整保存；静态定义从指纹匹配的GAME DATA读取；体积巨大的S／D地图与事件状态也保存完整当前bytes， 并按format_version=2的Zstandard合同压缩后编码为RFC 4648 Base64。

    实现已加入独立S／D编解码入口，使用固定Zstandard 1.5.7静态库及其官方API。先严格解码Base64，再检查普通单帧、content size、checksum标记与无字典，按固定输出容量解压并核对实际长度；不改变输入状态。此入口已由完整TOML内存快照与单文件读写调用，Legacy三文件事务已接入游戏保存，验证进度见实现清单。

  • 不允许[[items]]、[[scenes]]、[[magics]]或完整[[shops]]定义表； 物品名称、效果、武功数值、场景定义、商店商品与价格都由当前GAME DATA提供。

Legacy转换：先完整读取D／R／S，再将旧R存档中不可变部分与当前基线比较： 物品除user外的字段、场景元数据除entrance_condition外的字段、全部武功定义、商店商品ID与价格、角色id与head_id必须一致；

不一致即拒绝转换。通过后完整保存当前队伍角色；Legacy无法证明已经离队的历史成员，故不保存其他角色。

全部已保存角色的ever_joined统一为false，全部无关联秘笈成功次数统一为0；不得反推旧历史。

item_state.users、入口条件和商店库存从Legacy R完整取得，S／D原始bytes按format_version=2的Zstandard合同压缩并编码为RFC 4648 Base64。

3.1.4 字段表示与数值宽度

  • 内存权威值：所有角色数值属性（包括生命、内力、伤势、中毒、能力、经验与修炼经验）和伤害、治疗、用毒、解毒、附加效果等战斗结算的输入、临时增量及结果，在NG1和后续周目都统一使用signed 64位；

    不能只把角色字段扩宽，却把poison_delta、伤害值或写回前中间量保留为16位。

    每步运算在溢出前检查signed 64位边界，并按该字段独立的游戏规则检查合法域；不得在运行期用wrapping_i16、隐式窄化或Legacy记录的word读写作为这些数值的权威结算。

    旧机器的16位回绕只作为原版事实保留，不是本设计的数值存储策略。

    剧情携带物数量用受检signed64增减，保留原首个同ID槽、首个−1空槽、满槽无动作和不删除零／负数量槽的执行语义；溢出时ID与数量均不提交。运行指令可留下的负数量或空ID非零数量不等于可保存状态，保存仍按非负数量、空槽−1／0与引用有效性检查。实现记录见实现清单。

  • 经验链路：人物累计经验experience、当前秘笈修炼经验item_experience和制作物品经验 make_item_experience均以signed 64位作为运行时权威值；

    战斗经验奖励、修炼经验奖励、制作经验变化、累计与升级／练功门槛比较也全程使用检查溢出的signed 64位。

    不能只把存档字段扩成64位，却在奖励、累加、比较或战斗临时变量中先截成16／32位。

    写新TOML时按合法64位值保存，不以原版16位经验容器设上限；写Legacy时才按各经验字段原版编码语义逐项验证16位可表示性，越界则拒绝保存，不回绕。

  • Legacy输入与输出：RANGER.GRP及Legacy D／R／S中原有字段保持原始16位布局；加载时先按各字段原版的有符号或无符号解释完整解码，再提升到signed 64位。启用NG+时，旧存档的抗毒完整保留合法解码值，不按周目夹值；关闭NG+时保留原版物品可越过100的行为，不改写旧文件。

    向Legacy保存时仅在序列化边界逐字段验证其可无损编码的16位范围与原有合法域，然后编码；有符号字段须在−32768～32767内，无符号字段须在0～65535内，例如原版人物experience=52000是无符号16位值，

    不能错误地用有符号上界32767拒绝。任一值越界时整次保存失败，旧文件保持原状；不得为适配旧格式而降低运行时属性、截断、夹值或回绕。

  • 新TOML输出与读回：直接写出这些权威逻辑整数的signed 64位值，不强加Legacy的16位上界；写前检查signed 64位范围、内伤的HurtMax(n, CFG)、中毒量的0～99及各字段不变量，不按其他数值的周目比较节点限幅； 读档时先解析全部整数token为signed 64位并通过同样的游戏规则校验后再提交临时状态。

    TOML整数能够承载64位不等于可以跳过游戏数值合法域验证。每个入选角色完整保存实际逻辑整数，不转为Legacyword；战斗中未持久化的临时数值不凭空写入存档。

  • 不扩宽的其他数据：这一约定不改变地图S／D完整bytes、资源静态定义、ID及物品用户、入口条件、商店库存等与角色／伤害结算无关的数据合同。

    item_state.users、入口条件、商店库存仍按原约定的16位字段域验证；S／D在解压后按原始little-endian 16位word解释，其完整字节结构不因新TOML支持64位角色数值而自动扩宽。

  • 每个已保存角色的name／nickname均为必需的TOML UTF-8字符串。

    保存时把当前Legacy Big5字段从开头解码到第一个NUL或10-byte末尾；读档时再编码为Legacy Big5。

    字符串不得包含NUL，无法编码为Big5或编码后超过10 bytes时拒绝读档；不足10 bytes的尾部统一以NUL补齐。物品、场景和武功名称不属于存档字段。

  • 装备名称等根据当前周目动态生成的显示后缀不持久化。加载后仍以基础ID、当前周目和当前规则生成。

内存编解码实现：已按本节固定结构写出与解析普通／通关TOML：13个根键、九个资产指纹、14个header键及每名入选角色的45个键均完整验证。指纹匹配后从RANGER建立候选，只覆盖队伍与曾入队角色、动态小状态和存档内完整S／D；编码后重新解析并逐值比较，失败不返回文本或候选。普通与通关用途、槽号、周目、UTC时间格式、signed64及原生字段域、Big5姓名、引用和角色集合均有检查。此层只处理内存，下述单TOML文件层已调用该验证；普通读档的游戏状态替换与下一周目转换仍待接入。

3.1.5 严格加载验证

  1. 加载前拒绝超过64 MiB的文件；只接受普通文件，不跟随最终路径的符号链接。
  2. 解析失败、重复键、未知键、别名、类型错误、缺少必需键、数组长度错误、索引重复、排序错误、数值越界、Base64错误、解压失败、解压长度错误或跨字段不变量失败时，拒绝整个存档。
  3. 验证format与目录／用途一致，版本精确匹配，slot与三位补零文件名一致，playthrough在CFG允许的1…Nmax范围内，全部资产指纹一致。

  4. 指纹通过后，从当前RANGER构造角色、物品、场景、武功与商店静态定义及未入队角色基线；普通读档的S／D当前状态只来自scene_archives解压结果，不用ALLSIN／ALLDEF补齐。

    ALLSIN／ALLDEF只用于资产版本验证以及创建新周目时的原始世界基线。

  5. [[roles]]的ID必须严格递增且不重复；每个当前队伍角色必须存在。

    ever_joined=false的角色只有在当前队伍中才允许存在；ever_joined=true的已保存角色即属于EverJoinedRoles。

    每个角色必须包含完整字段、固定长度数组和完整no_magic_count[ItemCount]。

  6. item_state.users长度必须等于ItemCount，入口条件长度必须等于SceneDefinitionCount， 商店库存必须精确为ShopCount×5；所有ID与引用必须处于当前资产域。
  7. scene_archives的两个字符串必须符合上述严格Base64与Zstandard合同；解压前分别设置4,915,200和440,000 bytes固定输出上限，解压后长度必须恰好匹配，并拒绝尾随数据和多个frame。 成功后整块装入临时S／D存储。
  8. 库存严格按inventory数组顺序恢复到从0开始的连续槽位；第1.3节的物品继承白名单只在从通关存档创建下一周目时执行，不能用于普通读档。
  9. 全部状态写入临时快照后，再验证生命／内力当前值、武功槽与熟练度、装备、修炼物、携带物、库存引用、物品user、隐藏成功次数及全部ID的正文合法域和引用关系。
  10. 加载普通TOML时，只有临时状态通过全部验证后才一次性替换当前游戏状态。通关TOML不得直接替换游戏状态，只能生成下一周目的临时状态；任何失败都不得部分修改当前状态、GAME DATA或源存档。

3.1.6 原子写入与槽位

  1. 先在内存中完成序列化，再重新解析并按本节完整验证；回读验证失败时不得修改目标文件。
  2. 在目标目录以原文件名加.tmp排他创建普通文件，写入完整UTF-8 TOML并确认不超过64 MiB；刷新文件内容成功后才关闭。

  3. Windows使用ReplaceFileW；目标不存在时使用带MOVEFILE_WRITE_THROUGH的MoveFileExW。

    POSIX使用同文件系统rename并fsync目录。成功后目标只能是完整旧文件或完整新文件。

  4. 任一步骤失败时删除本次创建的临时文件并保留原目标。启动扫描忽略遗留.tmp，不得把它显示或加载为存档。

  5. 普通读档页面按槽号升序，每个编号最多显示一个逻辑槽位。enabled=true时优先显示普通TOML，没有TOML才显示Legacy；

    enabled=false时只显示Legacy。通关存档只在启用NG+后的“New Game+”来源页面显示。

    普通TOML和通关TOML文件名固定为三位补零001…999。

  6. 删除普通槽位时只删除当前优先级实际选中的格式：启用NG+且存在TOML时只删除该TOML，若同号Legacy仍存在，它随后成为可见后备；否则删除Legacy D／R／S。关闭NG+时只允许删除Legacy。删除成功后才刷新列表，且不得连带删除同号的另一格式。
  7. 关闭NG+时不创建、扫描、显示或加载TOML；磁盘上已有TOML不得自动删除或改写，重新开启NG+后恢复按TOML优先级处理。

单文件实现：已加入普通／通关槽位的安全读取与写入接口，验证全部001…999路径；读取通过原生句柄拒绝最终符号链接及非普通文件，分配前检查64 MiB限制，完整读取并拒绝提前EOF与长度变化。写入先完成内存回读验证，再排他创建.tmp，完整写入、刷新并关闭后调用本节的平台替换接口；新建目录同步其父目录。读取旧目标前排他建立.rollback.tmp占用，有旧档则写入并刷新其副本，无旧档则保持空占用；它持续保护重命名后的提交及回滚，避免第二个写入进入该窗口，以覆盖ReplaceFileW部分失败会改变旧文件名的情况以及替换后的目录刷新失败。原目标未变时不重复覆盖，已经改变时恢复旧副本；成功与可恢复失败均清理本次临时文件，不删除其他写入者或先前遗留的同名文件。若恢复或清理操作本身再次失败，接口明确返回错误和遗留路径，并保留旧副本，不把它报告为保存成功；此时未证明原目标路径已恢复，仍需上层处理。Linux完整158项回归通过；补入同槽位重入保护后，Linux与Windows两项原生文件／TOML槽位专项均通过；这不证明断电恢复、Legacy多文件事务、游戏界面接入或完整游戏链路已经完成。

Legacy三文件事务：游戏保存先同步当前坐标并导出一次完整逻辑快照，完整检查Legacy可表示范围、生成R字节后，才准备S／D／R的排他临时文件与旧档副本；全部写入、刷新和关闭后，依次替换S／D／R并同步目录。提交前任何可恢复失败均逆序恢复已尝试替换的文件，原先不存在的文件撤销新建；恢复一项失败仍继续恢复其余文件，并保留失败项的副本或占用及全部恢复路径。整组替换与目录同步成功后才进入清理；此时若清理失败，明确报告“新档已写入但临时文件清理失败”，不回滚已提交的新档，也不宣称旧档已恢复。游戏错误处理记录恢复路径；Legacy完整加载与列表预览遇到该槽位的事务遗留文件时拒绝读取。已有临时文件不由新事务删除。该实现不承诺三次重命名对其他进程同时可见，不证明断电恢复；跨平台验证进度见实现清单。

3.2 隐藏次数与持久化

ItemCount = 当前物品定义数量
H0 = 原版无关联武功秘笈首次费用阶级
no_magic_count[role_id][item_id] ≥ 0，须可用signed 64位表示  # 不以周目节点封顶
item_id ∈ [0, ItemCount－1]
仅当 magic(item_id)=-1 且 need(item_id)>0 时允许no_magic_count非0
NG+转换：role_id∈EverJoinedRoles时原样继承；其他角色的no_magic_count保持基线值0

隐藏次数不是“当前装备这本书的临时值”，而是角色对每一本无关联秘笈各自的长期记录。角色把书丢掉、换成别的书、下一周目重新取得，原次数仍然存在，因此不能靠换书把费用刷回第一次。

  • 新增no_magic_count[ItemCount]，按角色保存、按物品ID索引；原版当前ItemCount=200。
  • 是否使用计数由当前物品定义中的magic_id与need_experience判断；其他位置必须为0。
  • EverJoinedRoles来自存档中的历代实际入队记录；其中角色的隐藏次数完整继承，未入队角色不写入TOML且隐藏次数保持基线值0。
  • practice_item和当前item_experience仍按周目转换规则清空，但历史成功次数不清空。
  • 隐藏次数不再有随周目确定的最大值；默认NG999节点换算所得的旧9988仅是比较位置，不限制NG1或NG999的实际次数。每次增长仍检查64位溢出。
  • 修炼经验累计值使用64位逻辑字段，不允许16位回绕。
  • 该字段按第3.1节写入All-in-One TOML；当前格式使用format_version=2、ruleset_version=3，不自动迁移旧格式。

3.3 边界与实现要求

Nmax = CFG允许的最大周目  # 限制周目序号，不限制该周目能练到的等级或次数
Mref(Nmax) = M0＋(Nmax－1)×martial_level_step  # 仅供旧表比较
CountRef = Mref(Nmax)－H0  # 旧方案的隐藏次数节点，不是最大次数
PaidTierRef = Mref(Nmax)－1  # 节点前一档，不是最高费用档
Amax = max(A(iq))，iq取当前角色字段允许域
NeedAssocMax = max(need(i))，magic(i)≥0
NeedUnassocMax = max(need(i))，magic(i)=-1且need(i)>0
WARmax = max(WAR(w))，w取当前战斗定义
Bmax = B(Nmax)

关联武功在该对照档的费用 = NeedAssocMax×Amax×PaidTierRef
无关联武功在该对照档的费用 = NeedUnassocMax×Amax×PaidTierRef
最大整场人物战斗经验 = floor(WARmax×Bmax÷100)
最大单场秘笈修炼经验 = floor(最大整场人物战斗经验×Pr÷100)

原版当前资产与默认配置核对：
Nmax=999，M0=10，martial_level_step=10，H0=2，Amax=7
NeedAssocMax=300，NeedUnassocMax=800，WARmax=5000
B2=150%，Bstep=100个百分点，Pr=80%
Mref(Nmax)=9990，CountRef=9988，PaidTierRef=9989
关联武功在该对照档的费用=20,976,900
无关联武功在该对照档的费用=55,938,400
最大整场人物战斗经验=4,992,500
最大单场秘笈修炼经验=3,994,000

既有NG999样本中，战斗经验可因Nmax和资产定义而得到上界；武功等级、秘笈成功次数及其费用却不再有由Nmax推得的最大值。上方旧费用数值只是NG999对照档的核算结果，超出该档继续按同一费用公式增长；程序始终读取实际资产，使用经检查的64位中间量，不得拿对照值作为溢出安全证明。

  • NG+关联武功保持既定基础费用和熟练度增量，不以原版十级或周目节点阻止成功；无关联武功第一次使用H0，原版当前值为2，此后逐次涨价。
  • 默认NG999的9990级与9988次仅是比较节点；NG1至NG999均可继续超出各自节点修炼。
  • 默认NG999关联武功在对照档的费用为20,976,900，无关联武功为55,938,400；不是最大单档费用。
  • 默认NG999最大整场人物战斗经验为4,992,500；对应单场秘笈修炼经验为3,994,000。
  • 人物费用、奖励，以及伤害、治疗、内伤、中毒与解毒结算全链路均按第3.1.4节使用signed 64位权威值和经检查的中间量；只有写出Legacy存档时才按字段原版16位编码校验，不把Legacy字宽带回运行期。
  • 换周目不自动增加任何已继承的人物经验、武功熟练度、秘笈成功次数或永久属性；内伤、中毒换周目清0；内伤保留周目上限HurtMax(n, CFG)，中毒量正常范围固定为0～99。
