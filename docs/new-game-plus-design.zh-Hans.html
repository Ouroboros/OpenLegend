1. 人物、物品与战斗经验

1.1 数据事实与术语

  • WAR.STA中的经验是整场战斗总经验，不是单个敌人的经验。
  • 战斗结束后先按原规则确定胜负、存活资格和人数，再得到每名角色的原始个人奖励e0。
  • 下文所有“战斗所需场数”均使用整场总经验且不做队伍分配；多人存活时，每人的实际经验还要先按原规则分配。
  • 原版当前数据中，战斗99由5名番僧组成、整场经验450且可以重复触发，因此用作低收益可重复战斗样本；程序仍按战斗定义读取。
  • 秘笈修炼经验指item_experience；它与战斗中使用武功获得的1／2点熟练度不是同一个系统。

1.2 人物数值继承

本节处理原版角色记录中已经存在的字段，并额外包含已经明确批准的unassociated_manual_success_counts[ItemCount]。除该字段外，其他NG+新增字段、装备物品自身记录、库存、队伍、剧情状态和其他系统设计不属于本节。

1.2.1 范围与通用公式

Prev(r,f) = 源通关TOML的[[roles]]中角色r的完整逻辑字段f
Base(r,f) = 当前原版RANGER角色定义中的字段f
Cap(f,n) = 按当前规则集与运行时CFG求得的字段f在第n周目的合法上限
EverJoined(r) = 角色r是否曾在任一周目实际加入过队伍
RoleId(r) = r                                  # 固定身份不变量
HeadId(r) = Base(r,head_id)                     # 固定头像定义，不写入TOML

TOML中的角色ID重复、越界或顺序错误：拒绝转换
Legacy源存档中的角色ID或head_id与当前原版角色定义不一致：拒绝转换

不参与继承且不受EverJoined范围限制的原版字段集合：
FreshFields = { sexual, taking_items[4], taking_counts[4] }
对于所有角色r和f∈FreshFields：
Next(r,f) = Base(r,f)

其中角色携带物的恢复必须逐角色读取当前原版数据：
Next(r,taking_items[0..3]) = Base(r,taking_items[0..3])
Next(r,taking_counts[0..3]) = Base(r,taking_counts[0..3])
不得硬编码任何角色ID、物品ID或数量
不得在NG+转换阶段调用、重放或模拟KDEF剧情脚本

对于FreshFields以外的字段，若 EverJoined(r)=false：
Next(r,f) = Base(r,f)

对于FreshFields以外的字段，若 EverJoined(r)=true且字段采用直接继承：
Next(r,f) = clamp(Prev(r,f), Min(f), Cap(f,n))

对于FreshFields以外的字段，若 EverJoined(r)=true且字段恢复原版基线：
Next(r,f) = Base(r,f)

name与nickname继承逻辑字符串并执行UTF-8→Legacy Big5验证；
资源引用和数组槽位不使用数值clamp，复制后执行合法性验证。

角色ID与头像ID都属于固定角色定义，不参与继承、重置或clamp；TOML只保存角色ID，头像ID始终从当前原版角色定义读取。性别与角色原版携带物不受历史入队范围限制：所有角色进入新周目时都从当前原版角色定义恢复这些字段，不继承上一周目的变化。这样敌人重新取得原版战斗携带物，可入队角色也能按原流程在每个周目转交一次原版物品。除这些字段外，只有曾经真正加入过队伍的角色才执行下面的逐字段转换；未入队角色不写入TOML，新周目直接使用当前RANGER角色基线。直接继承不是把数值补到新上限，而是先复制实际值，再防止非法越界。

1.2.3 转换顺序与示例

  1. 从当前原版RANGER.GRP读取角色基线与字段合法域。
  2. 判断角色是否属于“曾在任一周目实际加入过队伍”的名单。

2.1.3 统一结算顺序

I' = I＋T

若 I'＜C：保存 I'，本场不完成
若 I'≥C：本场完成一次，执行一次对应效果，然后令 I=0
同一场战斗不得再次检查下一档

本场修炼经验先加进当前进度。不够就留下以后继续攒；够了就只成功一次、执行一次升级或永久属性效果，然后把进度清零。即使多出来很多经验，也不会同一场连升多级，多余部分仍然丢掉。

  1. 人物经验按存活和人数规则分配并乘人物周目倍率。
  2. 秘笈修炼经验按Pr取实际人物经验的比例；原版当前为80%。
  3. 累计经验不足下一档费用时保留。
  4. 达到费用时，本场最多完成一档。
  5. 执行一次原学习／升级／永久属性效果。
  6. 当前item_experience清零，超过费用的部分丢弃。

不设置独立修炼周目倍率；旧方案的222%和Mn不使用。need_experience、magic_id和永久效果字段必须从当前物品定义读取，不能针对表中六本秘笈写死数值或效果。

Kstart(n) = Lcur(n－1)
Kend(n) = Lcur(n)－1
Ck = 物品i、角色iq和阶级k代入对应费用公式后的结果

3. 持久化与实现约束

3.1 NG+ All-in-One TOML存档

启用NG+后，从一周目开始，普通存档和通关存档都以一个UTF-8 TOML文件保存恢复游戏所需的状态。加载时先从指纹匹配的当前GAME DATA建立静态定义，再按数据性质恢复：权威运行状态完整保存，静态定义只引用GAME DATA，S／D世界状态分别保存为完整bytes，经Zstandard压缩后编码为Base64。All-in-One表示这些状态与NG+扩展都在同一个TOML中，不使用sidecar。

3.1.1 格式分流与用途

[new_game_plus]
enabled = false  # 是否启用NG+存档格式与加载优先级
条件与用途保存格式路径
enabled=false的普通存档现有Legacy D／R／S，字节布局不扩充存档根目录中的R1.GRP／S1.GRP／D1.GRP … R999.GRP／S999.GRP／D999.GRP；继续共享原版RANGER.IDX
enabled=true的全部周目普通存档GAME DATA静态基线＋分类持久化状态的All-in-One TOML；一周目起即使用ngplus/001.toml … ngplus/999.toml
enabled=true的一周目起通关存档相同结构、只用于创建下一周目的All-in-One TOMLcompleted/001.toml … completed/999.toml

    若 enabled=true：TOML > Legacy D／R／S
若 enabled=false：只读取 Legacy D／R／S
  • enabled=true时，同槽位存在普通TOML就只验证并加载TOML；只有不存在TOML时才读取Legacy D／R／S。TOML存在但损坏或不兼容时必须报告错误，不得静默回退到可能较旧的Legacy状态。
  • enabled=false时，普通读档扫描、列表和加载都只处理Legacy D／R／S，完全忽略普通TOML和通关TOML；磁盘上的TOML保持不变。
  • Legacy读档路径始终保留：关闭NG+时它是唯一读档格式；开启NG+时它是同槽位不存在TOML时的后备格式。关闭NG+时普通保存继续写Legacy；开启NG+时无论当前是第几周目，普通保存都写All-in-One TOML。
  • 保存格式不决定运行时属性宽度：角色数值属性及伤害、医疗、内伤、中毒、解毒等战斗结算数值在内存中统一为signed 64位。向Legacy D／R／S写出时，须在任何16位编码之前逐字段检查原版对应的有符号／无符号16位可表示范围及字段合法域；任一值不能无损表示即拒绝整次保存，保留原存档，不截断、夹值或回绕。写入新TOML时，这些逻辑整数直接使用signed 64位，不因Legacy格式另加16位限制；校验仍包括本周CFG上限和字段不变量。只对实际写入存档的字段做编码检查，战斗临时伤害量不会因此变成Legacy存档字段。详细边界见第3.1.4节。
  • 开启NG+后加载Legacy存档时，本次加载仍按Legacy格式完整读取；其后执行普通保存时写入新的TOML，不覆盖或扩写原Legacy文件。此后同槽位读档由TOML优先。
  • Legacy没有NG+专属历史字段。转换时，每名角色的ever_joined统一初始化为false（逻辑值0），全部unassociated_manual_success_counts[ItemCount]统一初始化为0；不得根据当前队伍、剧情状态、人物属性或物品状态反推旧历史。转换后的正常入队与无关联秘笈成功事件再从这些初始值开始记录。
  • 两类TOML都不使用sidecar，不混合读取同槽位D／R／S，也不能导出为Legacy格式。不得用一种统一的“全存”或“全差量”策略处理全部数据；各类状态必须严格使用第3.1.3节规定的完整状态、静态引用或完整压缩bytes表示。
  • 普通TOML可从存读档界面直接恢复游戏；通关TOML只能由标题菜单的“New Game+”入口读取，不能作为普通存档加载。
  • 一周目通关TOML也使用本节定义的完整结构；从通关TOML创建下一周目时，才执行第1章规定的人物、物品、故事状态和新周目初始状态转换。
  • 同一编号的Legacy与普通TOML可以同时存在于磁盘，但普通读档界面把它们视为同一个逻辑槽位并按上述优先级选择来源。通关TOML位于独立目录，只出现在启用NG+后的“New Game+”来源页面。

  • 内存权威值：所有角色数值属性（包括生命、内力、伤势、中毒、能力、经验与修炼经验）和伤害、治疗、用毒、解毒、附加效果等战斗结算的输入、临时增量及结果，在NG1和后续周目都统一使用signed 64位；不能只把角色字段扩宽，却把poison_delta、伤害值或写回前中间量保留为16位。每步运算在溢出前检查signed 64位边界，并按该字段独立的游戏规则检查合法域；不得在运行期用wrapping_i16、隐式窄化或Legacy记录的word读写作为这些数值的权威结算。旧机器的16位回绕只作为原版事实保留，不是本设计的数值存储策略。
  • 经验链路：人物累计经验experience、当前秘笈修炼经验item_experience和制作物品经验make_item_experience均以signed 64位作为运行时权威值；战斗经验奖励、修炼经验奖励、制作经验变化、累计与升级／练功门槛比较也全程使用检查溢出的signed 64位。不能只把存档字段扩成64位，却在奖励、累加、比较或战斗临时变量中先截成16／32位。写新TOML时按合法64位值保存，不以原版16位经验容器设上限；写Legacy时才按各经验字段原版编码语义逐项验证16位可表示性，越界则拒绝保存，不回绕。
  • Legacy输入与输出：RANGER.GRP及Legacy D／R／S中原有字段保持原始16位布局；加载时按各字段原版的有符号或无符号解释解码，再无损提升到signed 64位逻辑状态。向Legacy保存时仅在序列化边界逐字段验证其可无损编码的16位范围与原有合法域，然后编码；有符号字段须在−32768～32767内，无符号字段须在0～65535内，例如原版人物experience=52000是无符号16位值，不能错误地用有符号上界32767拒绝。任一值越界时整次保存失败，旧文件保持原状；不得为适配旧格式而降低运行时属性、截断、夹值或回绕。
  • 新TOML输出与读回：直接写出这些权威逻辑整数的signed 64位值，不强加Legacy的16位上界；写前仍检查signed 64位范围、本周CFG字段上限及跨字段不变量，读档时先解析全部整数token为signed 64位并通过同样的游戏规则校验后再提交临时状态。TOML整数能够承载64位不等于可以跳过游戏数值合法域验证。每个入选角色完整保存实际逻辑整数，不转为Legacyword；战斗中未持久化的临时数值不凭空写入存档。
  • 不扩宽的其他数据：这一约定不改变地图S／D完整bytes、资源静态定义、ID及物品用户、入口条件、商店库存等与角色／伤害结算无关的数据合同。item_state.users、入口条件、商店库存仍按原约定的16位字段域验证；S／D在解压后按原始little-endian 16位word解释，其完整字节结构不因新TOML支持64位角色数值而自动扩宽。
  • 每个已保存角色的name／nickname均为必需的TOML UTF-8字符串。保存时把当前Legacy Big5字段从开头解码到第一个NUL或10-byte末尾；读档时再编码为Legacy Big5。字符串不得包含NUL，无法编码为Big5或编码后超过10 bytes时拒绝读档；不足10 bytes的尾部统一以NUL补齐。物品、场景和武功名称不属于存档字段。
  • 装备名称等根据当前周目动态生成的显示后缀不持久化。加载后仍以基础ID、当前周目和当前规则生成。

4.1 原版医疗与伤势机制

本节的actor是执行医疗的角色，target是接受医疗的角色；trunc表示向零取整，RNG.bounded(k)会取得0到k−1。以下至第4.1.1节之前均为原版行为说明，不代表伤势上限或医疗能力在NG+中已经决定扩展。

原版医疗作用距离

医疗目标距离 = trunc(actor.medicine ÷ 15) + 1

医疗能力每完整增加15点，目标距离才增加1级；0～14得到1，15～29得到2，30～44得到3。能力没有跨过下一个15点门槛时，不会提前增加距离。这是原版函数本身的算式；NG+规定的跨周目医疗距离上限见第4.1.1节。角色解毒的原版距离见第4.2节，主动用毒的原版距离见第4.3节；不能由医疗距离自动推定它们的NG2+距离。

医疗基础恢复量

m = max(actor.medicine, 0)

若 target.hurt ≤ 25：BaseHeal = trunc(4m ÷ 5)
若 26 ≤ target.hurt ≤ 50：BaseHeal = trunc(3m ÷ 4)
若 51 ≤ target.hurt ≤ 75：BaseHeal = trunc(2m ÷ 3)
若 target.hurt > 75：BaseHeal = trunc(m ÷ 2)

伤势越重，同一医疗能力能够恢复的HP比例越低。四档依次只取医疗能力的80%、75%、约66.7%和50%；这一步只计算HP恢复量，不决定伤势减少量。例如医疗能力为60时，目标伤势50会得到45点基础恢复，伤势51则立即降为40点基础恢复。

成功判定与最终结果

Heal = BaseHeal + RNG.bounded(5)       # 在基础值上增加0～4

若 target.hurt > actor.medicine + 20：
  Heal = 0
  本次不降低伤势
否则：
  target.hp = min(target.maximum_hp, target.hp + Heal)
  target.hurt = max(0, target.hurt - m)

医疗先按伤势档位计算恢复量，再增加0～4点随机值。随后才检查医疗能力是否足以处理当前伤势：目标伤势比医疗能力高21点或更多时，恢复HP和降低伤势都会失败；恰好只高20点仍然成功。成功时，HP最多补到生命上限，但伤势直接减去完整的医疗能力，而不是减去折算后的BaseHeal。

例如medicine=60、hurt=50时，理论HP恢复为45～49，伤势会从50降到0；如果目标只缺20点HP，实际只补20点，但伤势仍会降到0。若同一角色面对hurt=81，因为81大于60＋20，本次医疗完全失败；hurt=80则仍可成功。

  • 战斗菜单要求physical_power>50且medicine≥20才显示医疗可用；核心医疗计算本身在体力低于50时直接失败。也就是说，菜单条件与底层函数对体力50这个边界并不完全相同。
  • 医疗核心计算消耗2点体力，战斗共享行动尾部再消耗2点，因此一次战斗医疗通常共消耗4点体力；非战斗队伍菜单只调用核心计算时消耗2点。
  • 武功造成HP伤害后，目标增加trunc(damage÷10)点伤势并封顶99。受到39点伤害会增加3点伤势，受到40点伤害会增加4点。
  • 目标已有伤势会使本次武功伤害额外增加trunc(hurt÷20)。伤势40会让每次武功伤害再增加2点，伤势80会增加4点，因此伤势会放大后续损失。
  • 每轮行动值还会扣除trunc(hurt÷40)，所以伤势0～39没有该项惩罚，40～79扣1，80～99扣2。
  • 回合状态结算会扣除trunc(hurt÷20)点HP；伤势0～19时不扣HP，40点每轮扣2点，99点每轮扣4点。
  • 治疗物品和伤害型暗器走各自独立的物品公式，也能降低或增加hurt，最终仍限制在0～99；它们不调用上述角色医疗成功判定。

因此伤势不是单纯的显示数值：它同时降低角色医疗的HP恢复效率、提高后续武功伤害、降低行动值，并在回合结算时继续扣HP。角色医疗成功后则会同时处理HP和伤势，两种结果使用不同的计算量。

4.1.1 医疗距离、准入与治内伤规则（已确认部分）

4.3 原版施毒与抗毒路径（机器事实）

以下只审计原版不同来源的施毒增量与抗毒门槛：主动用毒、武功附毒、普通物品与玩家／AI投掷各走独立路径。玩家投掷带毒暗器时技巧项的原版减号仅是机器事实，NG1起的正式改号规则见第4.4节；各路径抗毒条件保留，不把原版封顶99直接当成NG2+已批准的写回公式。原版主动用毒目标距离为trunc(actor.use_poison÷15)+1；角色解毒与中毒回合扣血的正式规则见第4.2节。

主动用毒

ActivePoison = trunc((actor.use_poison - target.anti_poison) ÷ 4)
ActivePoison = clamp(ActivePoison, 0, 99 - target.poison)
target.poison += ActivePoison

主动用毒先用施毒者的use_poison减去目标的anti_poison，每剩余4点差值才增加1点中毒。抗毒等于或高于用毒时结果为0；目标已经接近99时，只补到99，不会溢出。例如use_poison=80、目标anti_poison=40时，理论增加10点；若目标已经有95点中毒，实际只增加4点。

物品与暗器的三条独立中毒路径（原版事实）

设V=item.add_poison、W=actor.hidden_weapon、A=target.anti_poison、P=target.poison。trunc始终向零取整，负值不能改用向下取整；R1、R2是中毒分支先后取得的两个RNG.bounded(5)（各0～4），signed16表示取低16位再按有符号数解释。下列简式用于正常合法数值域；写回时仍按原版16位回绕与路径专属clamp处理，不得外推为NG+数值域。

普通物品效果（战斗使用物品／非战斗物品／AI普通物品）：
  V > 0：x = trunc((W + V) / 2) − A
         Δ = (A ≥ 100 或 x < 0) ? 0 : trunc(x / 2)
  V < 0：Δ = trunc(V / 2) + R1 − R2
  V = 0：跳过中毒字段和中毒分支RNG；P不变

玩家战斗投掷暗器：
  V > 0：x = signed16(trunc((V − W) / 2) − A)
         Δ = (A ≥ 100 或 x < 0) ? 0 : trunc(x / 2)
  V ≤ 0：Δ = trunc(V / 2) + R1 − R2  # V恰为0仍取两次RNG

AI战斗投掷暗器：
  V ≥ 0：Δ = V
  V < 0：Δ = signed16(trunc((V − W) / 2))
  # 这条路径既不读取A，也不为中毒变化额外取得R1／R2

以上进入中毒写回的分支：P' = clamp(signed16(P + Δ), 0, 99)

原版正毒普通物品先将W与V相加；原版玩家投掷却从V减去W，后者从NG1起按第4.4节改为加号。两条原版正毒路径在中间值为负或A≥100时归零，再向零除以2。负毒普通物品与玩家投掷不读抗毒，随机差范围−4～＋4；玩家投掷的V=0也会进入这一随机分支，普通物品的V=0则跳过整个中毒结算。AI投掷正毒直接把V加到中毒，即使抗毒达到100也不被该能力阻止；负毒按(V−W)/2向零取整且不追加中毒随机数。这里说的是中毒分支自身的RNG，不排除同一暗器动作另有伤害随机数。

队伍侧AI投掷还存在已核对的原版陈旧槽异常：动画和库存消耗使用当前选定物品，实际HP／伤势／中毒载荷却从最近一次有效玩家物品确认槽读取；敌方AI仍从当前来源槽读取。因此AI公式中的V是实际载荷物品的add_poison，不一定是本次显示或消耗的物品值。现阶段只记录原版事实，不把三条路径合并，也不据此批准NG+用毒扩展。

4.4 玩家投掷带毒暗器时技巧项的全周目改号规则（已确认）

这是相对第4.3节所列原版机器减号的明确新规则，从NG1起适用于所有周目。定位到src/battle/battle_setup.cpp原有if (item_poison > 0)分支：只把item_poison - actor.hidden_weapon中的暗器技巧前减号改成加号，即V − W改成V + W；此条件来自原代码，不是另加的“正毒”规则。减目标抗毒的减号及其他步骤不变。原版汇编事实仍保留在第4.3节；不能把本节新规则反称为原版行为或笔误修复。普通物品、AI投掷和玩家投掷V≤0的中毒分支不改。

V = item.add_poison > 0，W = actor.hidden_weapon，A = target.anti_poison
x = trunc((V + W) / 2) − A  # 原版机器在W前是减号；全周目均改为加号
Δ = (A ≥ 100 或 x < 0) ? 0 : trunc(x / 2)
# x、Δ与后续中毒状态结算一律使用检查溢出的signed 64位逻辑数值
